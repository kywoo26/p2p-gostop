# 상호작용 결정과 후속 인터뷰

2026-09-29 · 기준 main `ca66ce9` · 문서 전용, 구현 완료 아님.
근거: [spec §6·FR-14~17·FR-46~50](../../spec.md), [plan M3·M6·D2](../../plan.md), [UI 규범](ui-spec.md), [플레이 보조 조사](../research/play-assist.md), [규칙 §12](../research/rules-commercial.md#12-권장-기본-규칙-세트), [Galaxy 계획](../plan-galaxy-solo.md), [이번 1차 출처 조사](../research/interaction-conventions.md).

**확정**은 이번 사용자 인터뷰의 결정, **권고**는 아직 답을 받지 않은 후보, **기존**은 현행 명세다. 상용의 ‘일반적/일부/없음/미확인’은 출처의 판정이고 제품 채택 상태와 다르다. 확정 항목은 다시 승인받지 않는다. 아래 대안은 비교 기록이지 확정 결정을 되돌리는 질문이 아니다.

### 2.1 동등성·자동 선택 계약 초안

| 판단 단계 | 권고 계약 / 반례 |
|---|---|
| 동등한 대상 | 현재 자기 `pending.kind=target`의 legal 후보, 동일 달·동일 종류·동일 피 가치·동일 족보 기여·특수 역할 없음. 최초 범위는 **같은 달 일반피 1가치 두 장**. 표준 카드 카탈로그에서 ID/그림만 다른 쌍 |
| 다른 가치 | 피1/쌍피2, 열끗/띠, 국진/일반피, 홍단/기타 띠처럼 미래 족보·역할 차이가 있으면 묻기. 현재 0점 증가가 같다는 이유로 생략하지 않음(S1~S5). 월이 다르면 애초 같은 target 후보가 아님 |
| 우선순위 | 동등 후보 중 ID 오름차순을 **자체 권고**. 화면 좌우·DOM 순서·좌석·랜덤·더미 정보에 의존하지 않음. 이는 고득점 선택이나 상용 우선순위의 재현이 아님 |
| 질문 발생 시점 | 낸 패와 뒤집은 패에서 생긴 target 모두 같은 정책. 따닥 가능성을 미리 알아서 생략하는 것이 아님. 전체 무더기 획득은 target 비교가 아니라 엔진의 pile 처리 |
| 입력·재연결 | 권위 스냅샷/액션 ID로 1회, 기존 전송·중복 방지 경로 재사용. 렌더마다 재전송하거나 호스트·게스트가 같은 좌석을 각각 자동 실행하지 않음. 솔로/호스트/게스트 동일 정책, 이벤트·정산·로그는 수동 선택과 동일 |

### 2.2 ‘유일 합법 수’ 자동 진행 계약 초안

사용자는 **자동 진행 자체를 확정**했다. 아래는 안전하게 같은 의도를 구현하기 위한 경계다. 힌트 단계와 분리하며, 자동 동등 선택과 강제 수 실행만으로 힌트 사용 이력을 올리지 않는다.

| 상황 | 동작 / 이유 |
|---|---|
| 자기 play pending, legal에 일반 play 또는 flipOnly 하나뿐 | 직전 이벤트 재생 완료 뒤 그 수를 1회 자동 실행. ‘자동 진행’ 문구와 일반 카드 경로 유지. 추가 확인/타이머 없음 |
| 손패1 + 폭탄패 토큰 / 손패3 + bomb / 여러 보너스 | 모든 합법 행동을 세므로 하나가 아님. 손패 장수나 매칭 가능 장수만 보고 자동 내지 않음 |
| target 2개가 규칙상 동등 | legal 길이는 2여도 C01로 자동 대표 선택. 가치가 다르면 수동. 자동치기 일반 옵션을 켰다는 전제 없음 |
| 흔들기·국진·고스톱·총통 | 의미 있는 선택이 있으므로 수동. 엔진 규칙 자체가 선택을 없앤 자동 총통은 기존 처리 유지 |
| 판 종료 후 legal에 push 하나 | **자동 실행하지 않음**. ‘받기’는 세션 API라 legal 배열 밖에 있음. 전체 사용자 선택이 하나라는 뜻이 아님 |
| 메뉴/상세 보기·백그라운드·연결 단절·응답 대기 | 새 자동 입력은 보류 **권고**. 복귀한 최신 뷰에서 다시 판정, 오래된 예약 액션 폐기. 상대/AI의 이미 수락된 진행을 되돌리지는 않음(U14) |
| 연속 강제 수·보너스 보충 | 매 권위 뷰마다 다시 판정. 여러 턴을 몰아서 전송하지 않고 스킵 입력을 카드 입력으로 재사용하지 않음 |

## 3. 후속 인터뷰 문항

아래는 **미확정 항목만** 묻는다. 각 행은 ‘왜 / 권고·대안 / 질문·선택지’ 3개 정보 단위다. C01~05의 확정 내용은 재질문하지 않는다. 기존 명세를 바꾸는 대안이 선택되면 §5의 문서·수용 기준을 함께 갱신해야 한다.

## 4. ‘확정 획득’ 판정 초안 — 사용자 정의 고정

### 4.1 의미와 판정식

**같은 달 짝이 바닥에 있고, 그 달의 4장이 모두 내 손패·바닥·양쪽 획득패에 있으며, 미공개 집합에 그 달이 하나도 없으면 ‘확정 획득’. 그 달이 하나라도 미공개이면 ‘먹을 수 있음’이다.** 두 정상 예시를 다른 색·등급으로 나누지 않는다. 기본 힌트에서 이 두 범주를 표시하는 것을 권고한다(C05, D06).

`viewer`의 손패 카드 X의 달을 M이라고 한다. 보너스는 달이 없으므로 이 판정 대상이 아니다. `H_M`은 내 손패의 M 카드 집합, `F_M`은 바닥의 M 카드 집합, `C_M`은 **양쪽 모든 획득 그룹**의 M 카드 집합이다. 국진을 열끗/피로 표시하는 위치와 무관하게 ID를 한 번만 센다. `U_M`은 `unseenCards(view)`에서 M인 카드 집합이다.

| 조건 | 판정 계약 |
|---|---|
| 유효한 현재 입력 | 자기 차례·자기 play pending·최신 렌더 뷰이며 X의 play가 `view.legal`에 있어야 활성 표시. 재생/응답 대기·연결 단절 중에는 활성 표식 제거. 다른 pending을 UI에서 play로 가정하지 않음 |
| 바닥 짝 존재 | `matchPreview(view, viewer, X)`가 take/choose/pile이고 `F_M`이 비어 있지 않아야 함. place는 아무 표식도 주지 않음 |
| **확정 획득** | 위 조건 + `H_M ∪ F_M ∪ C_M`이 M의 기본 카드 **4개 ID 전부** + `U_M`이 공집합. 카드 ID 중복·누락·불완전한 뷰는 보수적으로 판정 불가 |
| **먹을 수 있음** | 바닥 짝은 있지만 위 확정 조건 불충족. 특히 `U_M`에 1장이라도 있으면 이 표시만. ‘획득 확률’·추천 순위·점수 우열을 붙이지 않음 |
| 판정과 행동 분리 | 확정 획득은 자동 내기 명령이 아님. 여러 합법 수이면 사용자가 고름. 바닥 2장 가치가 다르면 확정 획득이어도 대상 선택 유지(C01) |
| 보장의 범위 | X를 지금 합법적으로 냈을 때 해당 월의 짝을 획득할 수 있다는 분류. 판 종료 전에 손에 남은 모든 패를 반드시 먹음·승리·득점·획득한 피가 영구 보존됨까지 뜻하지 않음(B3/B4·G1/G2). choose는 최소 1짝이며 바닥 2장 전부 획득을 뜻하지 않음 |

**현 API의 중요한 차이:** `unseenCards`는 상대의 숨은 손패∪더미이며, 상대가 흔들기로 공개한 `SeatView.revealed`도 미공개 집합에서 뺀다. 따라서 사용자 표현 ‘상대 손+더미’를 그대로 `unseenCards`의 완전한 정의로 쓰면 안 된다. **U_M=0만 검사하지 않고 지정한 세 영역이 M의 4장을 모두 포함하는지 함께 검사**한다. 상대 공개 손패는 C05의 허용 영역에 추가하지 않는다. 공개된 상대 패가 있을 때 숨은 패/더미의 실제 위치를 추측하는 알고리즘도 만들지 않는다.

UI 표현 권고: 확정 획득은 의미색 A+실선+‘확정 획득’, 먹을 수 있음은 의미색 B+점선+‘먹을 수 있음’. A/B의 실제 색은 디자인 리드가 기존 토큰·대비·폭탄색과 함께 확정한다. A/B는 미정 색 이름이며 별도 시각 테마가 아니다. 그림 위 색 채우기 대신 둘레와 예약 여백을 사용하고, 터치/키보드 초점에서 동일한 조건 설명을 준다. 기본/상세의 실제 표시를 FR-50 사용 이력에 남긴다. 힌트 끔에는 두 표식 모두 숨긴다.

### 4.3 공개 API 구현 가능성과 검증 인계

| 공개 경로 | 있는 기능 / 없는 기능 | 사용 계약 |
|---|---|---|
| [`legalActions`](../../packages/engine/src/legal.ts) → `playerView.legal` | 합법 play/bomb/flipOnly/선택 반환. 입력은 GameState이므로 UI가 PlayerView로 직접 호출하는 함수는 아님 | UI는 이미 전달받은 legal을 소비. 게임 종료 push 하나의 자동화 반례 유지 |
| [`matchPreview`](../../packages/engine/src/preview.ts) | PlayerView로 take/choose/pile/place/bonus·흔들기 후보 계산. 차례 검증·뒤집기 결과·‘확정’ boolean은 없음 | legal로 먼저 제한, 바닥 짝 유무에 사용. take라는 이름만으로 확정 판정 금지 |
| [`unseenCards`](../../packages/engine/src/determinize.ts) | PlayerView에서 보이지 않는 카드 ID **집합**, 상대 공개 손패·현재 턴 공개 카드는 제외 | M 존재 여부만 사용. 상대 손/더미로 나눠 추정하거나 다음 카드·확률·순위를 표시하지 않음 |
| [`PlayerView`](../../packages/engine/src/view.ts)·[`getCard`](../../packages/engine/src/cards.ts) | 자기 hand·양쪽 captured·floor·revealed, 공개 불변 카드 카탈로그 | 세 영역의 M 4장 ID 집합 확인. 이 추가 집계가 있어야 C05를 완성하며 **세 API 중 하나가 이미 완성 판정을 제공하는 것은 아님** |
| 제안 `captureCertainty(view, viewer, card)` | **아직 없는 순수 API**. 결과 후보: none/match/guaranteed와 공개 이유 코드 | 위 조건을 엔진 공개정보 보조로 구현·검증한 뒤 web에 제공. 호출자는 힌트/입력 잠금 처리. 이름·타입은 후속 API PR에서 확정 |
| P2P `BoardView` 경계 | 게스트 BoardView는 PlayerView의 rules/ctx 전체를 갖지 않음 | ui-spec UX-A02의 #81→#87 전달 계약을 확정 표식까지 확장. 호스트가 좌석별 공개 뷰로 계산한 결과만 전달하고 게스트에 비밀 상태를 보충하지 않음 |

후속 검증은 CF01~16 규칙 벡터/순수 함수 사례, 숨은 배치만 치환한 동일 PlayerView의 텍스트·색·ARIA·로그 동일성, 좌석 반전, 솔로/호스트/게스트 왕복·재접속, 기본/상세/끔 전환과 FR-50 사용 이력을 포함한다. 순수 계산에 실제 GameState·PRNG·상대 손패·더미 순서를 추가하거나 AI 탐색을 부르지 않는다. 규칙 벡터의 기대값은 §12와 C05에서 유도한다. 이번 PR에서 테스트 코드나 새 API를 만들지는 않는다.

## 6. 이번 문서 PR 검증 상태

지정 문서·현재 공개 엔진 API를 읽고, 공식 본문과 설명 이미지를 직접 대조했다. 상용 자동 선택 우선순위·흔들기 선언 전 팝업 형태·공식 영상 프레임/음성은 미확인으로 남겼다. 소스 코드·자산·의존성 변경은 없다.

개발 이미지 진입점 `docker compose run --rm dev npm ci`를 시도했으나 이 WSL 환경에서 Docker 연동을 찾지 못해 실패했고 `/var/run/docker.sock`도 없었다. 따라서 AGENTS §5의 lint/check/Node·브라우저 테스트/웹 빌드/E2E/Android 검사는 **실행 불가**, 호스트 대체 실행·도구 설치 없음. 이 문서의 설계안이나 기존 코드가 테스트 통과했다고 주장하지 않는다. Galaxy/iPhone 실기기·음원 청취 결과도 만들지 않았다.
